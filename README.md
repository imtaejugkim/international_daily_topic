# Steam 게임 트렌드 → 디스코드

매일 Steam에서 **무엇이 갑자기 떴는지**를 잡아내고, 왜 떴는지 조사해서,
**작은 팀이 만들 수 있는 게임 아이디어**로 바꿔 디스코드로 보낸다.

매일 **09:00 KST** 자동 실행.

## 역할 분담

```
도구:  "이거 볼 가치 있다" 로 좁혀주기 + 각각의 시장 맥락
사람:  영상 보고 / 해보고 → 재미 판단 → 아이디어
```

도구가 재미를 판단하려 들지 않는다. 영상 1분이면 아는 것이고, 데이터로 우회할 이유가 없다.
대신 **그 1분을 어디에 쓸지** 좁혀준다. 그래서 평가 기준은 깊이가 아니라 **정밀도**다 —
5개를 짚었는데 4개가 볼 가치 없으면 시간만 버린 것이다.

## 가장 중요한 숫자: 성공률

`noticed_rate` = 그 태그로 **최근 출시된 게임 중 리뷰 50개를 넘긴 비율.**

| 성공률 | 뜻 |
| --- | --- |
| 높다 | 들어갈 자리가 있다 |
| 낮다 | **고기 분쇄기.** 바빠 보이지만 들어가면 6개월 쓰고 안 보인다 |

태그에 게임이 5,000개 있다는 건 시장이 크다는 뜻이 아니다. 태그는 유저가 달아서
스팸과 방치된 빌드가 섞인다. **5,000개짜리 태그의 성공률이 400개짜리보다 낮은 경우가 흔하다.**
그래서 분모는 스토어가 말하는 총 개수가 아니라 **우리가 직접 리뷰 수를 재본 최근 출시작**이다.

## 왜 동시접속이 아니라 리뷰 수인가

동시접속은 **지금 붙잡고 있는 사람 수**지 **팔린 양**이 아니다. 2,000명 동접에
20달러짜리가 50만 장 팔린 게임이, 20만 명 동접 무료 게임보다 성공이다.
Steam은 판매량을 공개하지 않지만 **리뷰 수는 판매량에 비례**하므로, 매일 재면
"지금 팔리고 있나"에 가장 가까운 공개 지표가 된다.

굳어버린 거인(CS2 등)은 `settled_giants`에 모아 **무시 대상으로 표시**한다.

## 구조

```
[수집] steam_collect.py
  ├─ 게임별 리뷰 수 ← 판매량 대리지표. 매일 재면 증가 속도가 나온다
  ├─ 게임별 동시접속 ← 당일 신호
  ├─ 신작 전수 / 출시예정 인기순 / 동접 상위 100
  └─ 태그별 최근 출시작 + 각각의 리뷰 수 ← 성공률의 분모

[신호] steam_signals.py
  📊 tag_health         장르별 성공률 ← 핵심
  🚀 surging            리뷰가 빠르게 느는 중 = 지금 팔리는 중
  🌱 young_and_noticed  최근 60일 출시 + 이미 주목 = 비교 가능한 사례
  📅 upcoming_watch     출시 예정 ← 유일하게 늦지 않은 신호
  💤 settled_giants     무시 대상

[해석] .claude/skills/game-brief/SKILL.md
  Claude Code Action이 신호를 읽고 웹을 검색해 brief.json 을 쓴다
  1. 장르 판정 — 어디가 열려 있고 어디가 고기 분쇄기인가
  2. 볼 것    — 영상 찾아볼 가치가 있는 게임 + 스토어 링크
  3. 방향     — 데이터가 가리키는 것. 기획안은 쓰지 않는다

[전송] send_brief.py → 디스코드
```

전부 **표준 라이브러리만** 쓴다. Steam API 키도 필요 없다 — 쓰는 엔드포인트가 전부 공개다.

## Steam 데이터 출처

| 엔드포인트 | 쓰임 | 키 |
| --- | --- | --- |
| `store/appreviews/<appid>` | **리뷰 수·긍정률** (판매량 대리지표) | 불필요 |
| `store/search/results?infinite=1` | 신작 전수·출시예정·**태그별 출시작과 총 개수** | 불필요 |
| `store/tagdata/populartags` | 태그 사전 429개 | 불필요 |
| `ISteamUserStats/GetNumberOfCurrentPlayers` | 게임별 동시접속 | 불필요 |
| `ISteamChartsService/GetMostPlayedGames` | 동시접속 상위 100 | 불필요 |
| `store/api/appdetails` | 장르·출시일·가격·개발사 | 불필요 |

검색 응답에는 appid가 없고 `logo` URL 경로에만 들어 있어 정규식으로 복원한다.
리뷰 **본문**은 어떤 파라미터 조합으로도 JSON 대신 HTML이 와서 수집하지 않는다.

`GetTopReleasesPages`는 데이터가 2025년 2월에 멈춰 있어 쓰지 않는다.
SteamSpy는 보유자 추정이 필요해지면 보조로 쓸 수 있다.

## 쌓이는 데이터

```
data/steam/2026-11-17.json    그날 스냅샷 (동시접속 수 포함)
data/signals/2026-11-17.json  급등·신규·상승 판정 결과
data/briefs/2026-11-17.json   그날 브리프
data/games.json               게임별 장르·출시일·가격 (한 번만 조회해 재사용)
```

**이 폴더는 의도적으로 커밋한다.** 어제 숫자가 있어야 오늘 급등을 계산할 수 있다.

`archive-app-trends/`는 이전 프로젝트(국가별 앱·뉴스 트렌드)의 47일치 기록이다.
지금 파이프라인과는 무관하며 참고용으로만 남겨뒀다.

## Secrets

| 이름 | 필수 | 용도 |
| --- | --- | --- |
| `DISCORD_WEBHOOK_URL` | ✅ | 전송 대상 웹훅 |
| `CLAUDE_CODE_OAUTH_TOKEN` | ✅ | 브리프 작성. **Claude 구독으로 실행되어 API 요금이 따로 안 나간다** |

`CLAUDE_CODE_OAUTH_TOKEN`은 로컬에서 `claude setup-token`으로 만든다.
Console API 키(`sk-ant-...`)와는 **별개의 결제**다. 이 토큰은 만료될 수 있고,
만료되면 브리프 단계가 2초 만에 실패한다 — 그때 디스코드로 알림이 간다.

## 설계 메모

**실패작이 분모에 있어야 한다.** Steam이 미는 신작 30개만 보면 살아남은 것만 보인다.
태그별 최근 출시작을 통째로 받아 **리뷰가 거의 없는 게임까지 세야** 성공률이 나온다.

**동접 조회와 리뷰 조회의 대상이 다르다.** 동접은 살아있을 법한 게임만(요청이 아깝다),
리뷰는 태그 출시작 전부(실패작이 분모다).

**장르 간 리뷰 수를 직접 비교하면 안 된다.** 리뷰율이 장르마다 2~5배 차이 나는데
보정할 방법이 없다. 같은 태그 안에서만 비교한다.

**표본이 작으면 성공률이 요동친다.** 며칠치로 장르를 단정하면 안 된다.

**스토어는 거절이 아니라 지연으로 막는다.** `store.steampowered.com`은 과도한 요청에
에러를 주는 대신 응답을 끌어서, 타임아웃이 넉넉하면 수백 건이 몇 분짜리 수집을
한 시간짜리로 만든다. 그래서 스토어 대상 조회는 **시도 1회, 타임아웃 8초**로 두고
못 받은 건 그냥 건너뛴다.

**리뷰 수는 캐시한다.** 3주 전 출시작이 오늘 리뷰 4개면 내일도 4개다. 매일 다시 재는 건
신작·출시예정·동접 상위 같은 **움직이는 집합**뿐이고, 성공률 분모가 되는 태그 과거
출시작은 캐시가 묵을 때만 갱신한다. 태그도 하루 4개씩 순환해서 며칠에 한 바퀴 돈다.
이게 없으면 하루 요청이 1,000건을 넘는다.

**수집에 시간 예산이 있다.** 넘기면 거기까지만 저장한다. 하루치가 조금 비는 건 괜찮지만,
끝나지 않는 실행은 브리프 단계까지 못 가게 만든다.

**숫자는 "무엇이" 떴는지만 말한다.** "왜"는 검색해야 안다 — 출시, 할인, 업데이트,
스트리머 방송. 그래서 브리프 단계에 웹 검색이 열려 있다.

**게임 메타데이터는 한 번만 조회한다.** `data/games.json`에 쌓아두고 재사용한다.
매일 220개를 다시 조회하면 Steam 스토어 API가 막는다.
